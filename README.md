# Ulgamdagal AI Chat 0.9.36

Подготовлено 15 ноября 2026 поверх 0.9.35, работоспособность которой пользователь подтвердил на сайте. Новая версия пока не установлена. API/Portainer и схема базы не меняются.

## Настройки подключения

API-ключ, кнопка сохранения настроек и проверка соединения перенесены в самый верх страницы. Поля ключа связаны с общей формой настроек через HTML form attribute; сохраняются все настройки, а не только ключ. Формы не вложены друг в друга. Проверяется сохранённый ключ: после ввода сначала сохранить, затем проверить.

## Исправления

- request-status включён в Service_Guard: 60 запросов/мин на IP или IPv6 /64, 12/мин на сессию, общий предел восемь параллельных служебных операций, одна операция на сессию. Кеш результата 5 секунд, ошибки 2 секунды. Ключ кеша включает сессию, исходный request_id, сообщение, токен и курсор. Изменение сообщения не получает закешированный ответ другого запроса.
- Для восстановления первого потерянного ответа отсутствие conversation_token допустимо: его браузер ещё не получил. Если токен передан, подпись проверяется. Точный исходный request_id и fingerprint проверяются текущим API. Запрос состояния не запускает генерацию. Старый неатомарный лимитер этого маршрута удалён.
- Единое определение корзины IP для новых служебных ограничений и основного chat: обычный IPv6 /64; IPv4-mapped IPv6 нормализуется до конкретного IPv4, разные IPv4 больше не схлопываются. Подменяемые Forwarded-заголовки не используются.
- Недоступная/неподдерживаемая GET_LOCK возвращает 503 service_lock_unavailable, а не обычный 429. Занятая блокировка по-прежнему означает временный 429: это необходимое ограничение параллелизма, а не успешное выполнение запроса. Освобождение блокировок выполняется в finally и дополнительно shutdown-обработчиком при завершении PHP. Это не гарантия пережить обрыв БД или принудительное уничтожение процесса; требуется штатная поддержка именованных блокировок MySQL/MariaDB, SQLite/PlanetScale не заявлены.
- pending_products удаляется сразу после успешной обработки обычного ответа, в том числе повторного. После неопределённого результата остаётся до восстановления или истечения двух суток; ранее накопленные записи истекают по старому сроку.
- Однократная миграция прав/пояса перенесена с общего init на admin_init до регистрации обработчика сохранения. Проверка доступа остаётся закрытой для неадминистраторов до завершения миграции. В версии 0.9.35 миграция уже пройдена, повторного сброса операторов не будет.
- Меню журнала больше не регистрируется с read: для администратора manage_options, для локального оператора ulgamdagal_ai_manage_chats. Дополнительная проверка явного списка операторов остаётся.

## Что осталось отдельной задачей

Суточный лимит расходов остаётся на действующем API (client_limits / request_control.py); локальный второй суточный счётчик не возвращается. Защита от распределённого сетевого флуда требует nginx/WAF. За прокси адрес посетителя нужно настроить на доверенной стороне, иначе один REMOTE_ADDR продолжит объединять посетителей. Разрешения на удалённые правки, домены ссылок, ключи на сайт и полное удаление плагина не входят в это обновление. Ключи и переписки при отключении/обновлении автоматически не удаляются.

# WordPress 0.9.35 — первый этап защиты служебных маршрутов

Подготовлен локально 15 ноября 2026. На сайтах ещё не установлен. Серверный пакет и миграции не нужны; основа — плагин 0.9.34 и действующий API с миграцией 021.

## Что изменено

- operator-messages: максимум 30 запросов/мин на сессию и 180/мин на IP; ответ кешируется на 3 секунды отдельно по подписанному диалогу, курсору и режиму операции. Ошибка кешируется на 2 секунды. Проверка подписи и лимитов выполняется до выдачи кеша. Данные не кешируются в браузере или публичном CDN.
- conversation-close и operator-request: по 6 запросов/мин на сессию и 30/мин на IP для каждого действия. Закрытие не кешируется: повтор после потери ответа обрабатывает идемпотентный API. После успешного закрытия или приглашения оператора кеш состояния обновляется.
- На сессию допускается одна одновременно выполняемая служебная операция, на установку WordPress — восемь. Остальные запросы получают ошибку сразу, без ожидания освобождения блокировки. Лимиты не расходуют счётчик сообщений ИИ.
- Лимиты сериализованы неблокирующими именованными блокировками MySQL/MariaDB; блокировки освобождаются в finally. При недоступности блокировок или записи счётчика запрос не проходит. Требуется поддержка нескольких именованных блокировок на соединение; она проверяется до выполнения операции. Внешний persistent object cache должен быть согласованным между PHP-воркерами.
- Подписанный conversation_token теперь обязателен и для чтения сообщений локального оператора. По одному session_id получить ответы нельзя. Повторный обычный /chat без токена для уже привязанной сессии отклоняется до отправки сообщения оператору или ИИ; восстановление потерянного первоначального ответа через request-status сохраняется.
- Новые идентификаторы сессий создаются только через crypto.getRandomValues. Нет Date.now/Math.random как источника секретов. Без криптографического генератора чат останавливается с понятным сообщением. Старые действующие подписанные диалоги сохраняются. Опрос оператора не запускается до получения токена.
- В ответах Telegram разрешены только ожидаемые поля. Для сообщений: id, message, system; для состояния: active, waiting, messages; для приглашения: success, state; для закрытия: closed и совпадающий conversation_id. Неожиданная структура вызывает 502; лишние поля отбрасываются до изменения локального состояния.
- Для новых лимитов IPv6 группируется по /64. Адрес берётся только из REMOTE_ADDR. Настройка доверенных Cloudflare/nginx-заголовков в этот этап не входит: подменяемым заголовкам автоматически доверять нельзя.

Проверка: новый диалог → первый ответ AI → взять диалог оператором → сообщить уникальный код от оператора → вернуть AI → попросить повторить код. ## Установка
1. Загрузите ZIP через «Плагины → Добавить плагин → Загрузить плагин» и активируйте.
2. Откройте «Настройки → Ulgamdagal AI Chat».
3. Сохраните полный URL `https://api.ulgamdagal.com/v1/ai/chat` и API-ключ.
4. Добавьте `[ulgamdagal_ai_chat]` на тестовую страницу.
5. Откройте её как администратор и отправьте сообщение. Обычные посетители чат не видят, доступ к прокси им запрещён.

## Контракт gateway
По предоставленному владельцем примеру: запрос `{"message":"Salam"}`, успешный ответ `{"success":true,"answer":"Salam!"}`. Прокси проверяет строгое логическое `success: true` и непустую строку `answer`, затем возвращает браузеру внутренний формат `{"reply":"Salam!"}`. При `success: false`, неверном JSON или неверных типах возвращается безопасная ошибка без исходного тела ответа. HTTP 422 может означать несовпадение схемы. Для адаптации предусмотрены PHP-фильтры `ulgamdagal_ai_gateway_payload` и `ulgamdagal_ai_gateway_reply`.

Браузер обращается только к WordPress REST API. PHP добавляет X-API-Key при обращении к gateway. В браузер не передаются ключ, исходное тело ошибки gateway или настройки. URL — полный адрес endpoint, не базовый домен. Перенаправления запрещены; HTTPS и публичный адрес проверяются. Нативная проверка REST nonce WordPress используется совместно с правами manage_options.

Ключ хранится в базе WordPress, без шифрования на уровне плагина. Сохранённое значение не подставляется даже в поле настроек. Можно вместо базы задать `define('ULGAMDAGAL_AI_API_KEY', 'your-secret');` в wp-config.php: константа имеет приоритет. Не добавляйте реальный ключ в исходники плагина или переписку.

История показывается только в текущей вкладке, не сохраняется и не отправляется вместе со следующим вопросом. Сообщение передаётся вашему gateway и подключённому им провайдеру. Ответы выводятся обычным текстом, без исполнения HTML. Ограничение: один запрос за 5 секунд на администратора (transient, приблизительное ограничение, не защита от конкурентной нагрузки). Публичный запуск потребует отдельной защиты от злоупотреблений и ограничения расходов.

## Проверка на тестовом WordPress
- Без входа POST /wp-json/ulgamdagal-ai/v1/chat должен возвращать 401/403.
- Администратор без корректного X-WP-Nonce также не получает доступа.
- Корректный запрос с ответом gateway `{"success":true,"answer":"Привет!"}` отображает «Привет!» в чате.
- Ответы с `success: false`, отсутствующим success, пустым или нестроковым answer отклоняются.
- Пустой запрос или строка длиннее 8000 байт отклоняется.
- Ключ не появляется в HTML, JS или запросах браузера; поле ключа после сохранения пустое.
- Ошибки gateway не раскрывают его исходное тело; ответ с HTML отображается как текст.
- Две вставки шорткода работают независимо.

PHP и WordPress в локальной среде отсутствуют: проверка выполнения и сквозной запрос не проведены. Перед использованием нужны PHP lint и перечисленные проверки на тестовом сайте. Отключение плагина сохраняет настройки; автоматического удаления ключа при деинсталляции нет — удалите его через настройки до удаления плагина.
